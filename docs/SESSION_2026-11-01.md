По звёздам ориентир — не другие Telegram MCP, а серверы общего назначения: эталонный `modelcontextprotocol/servers` (~92k), Context7 (~64k), Chrome DevTools (~54k), Playwright (~38k), GitHub MCP (~34k). Этот проект уже жёстче типичного поля: read-only по умолчанию прячет запись из `tools/list`, аккаунты изолированы, отправка идемпотентна, секреты и loopback закрыты отдельно.

Имеет смысл перенять у лидеров другое.

- **GitHub MCP:** список инструментов сужать по правам ключа, а не отказывать в момент вызова. Сейчас грант из файла прав действует только при вызове, и модель всё равно видит `ban_user`.
- **Playwright и Context7:** маленькая поверхность и прогресс на долгих операциях. 116 инструментов уже режутся профилями, но отмены клиентом и `notifications/progress` в коде нет.
- **Filesystem:** корни файлов из MCP roots сессии, а не только из `MCP_FILE_ROOTS`.

Главные риски надёжности и безопасности:

1. Запись при `MCP_DESTRUCTIVE_APPROVAL=off` оставляет подтверждение в аргументе `"confirmed": true`, который ставит сама модель. По умолчанию сервер read-only, поэтому это срабатывает только после включения записи без второго флага.
2. База TDLib на диске без ключа шифрования библиотеки. Защита равна шифрованию тома.
3. На `/mcp` нет проверки заголовка `Origin`, которую требует спецификация Streamable HTTP.
4. Один bulkhead на всех клиентов демона, allow-list чатов пустой означает «все чаты», секреты на Windows не проверяют ACL.

В конце файла — порядок P0–P2 и список того, что копировать не стоит: сырой API, ресурсы с текстом чатов, sampling.
