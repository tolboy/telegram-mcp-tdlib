# Аудит реализации и приоритеты Telegram MCP

17 ноября 2026 года. Исходный обзор Grok от 16 ноября использован как список гипотез. Статус реализации сверялся с GitHub и кодом. База аудита — `master` на `e4a6fe9` и черновик PR #72 на `358698b`. Сравнение опирается на реализации выбранных сценариев. Производительность конкурентов и качество ответов моделей в этом аудите не измерялись.

Операторский список `TELEGRAM_BLOCKED_CHAT_IDS` принимает числовые ID чатов, включая отрицательные. Он имеет приоритет над allow-list и грантами, включая opt-in для чувствительных чатов. Текущая политика применяется к сохранённым курсорам, экспортам и уведомлениям ресурсов. Операции с неизвестным заранее целевым чатом и динамические папки требуют неограниченной области доступа.

Callback-режим входящих событий остаётся открытым. JSONL-выгрузку стоит оценивать при потребности конкретного клиента. У Chigwell это отдельный локальный режим для Claude Code. [Режим входящих событий Chigwell](https://github.com/chigwell/telegram-mcp/blob/0d27284a5e99d788ffe4f857d9df8d9d668e2820/README.md#incoming-event-feed-callback-mode-claude-code-only)

Ожидание с `chat_id` подходит для сценария «дождаться ответа в этом диалоге». Без `chat_id` тихое окно считается для всего видимого потока, поэтому один активный чат способен задерживать завершение других. Сохранение раздельных пачек для нескольких чатов потребует отдельно согласованного контракта курсоров.

На Windows один тест обслуживания сессии нестабилен и на исходной ревизии PR #72. Повторный диагностический прогон показал `AccessDeniedException` при переносе каталога сессии или публикации резервной копии. Сбой останавливает очистку до удаления данных. Для этого пути стоит отдельно измерить частоту отказов и проверить восстановление, сохранив текущие проверки доступа.

## Проверка исправлений

- На Windows и JDK 25 полный набор Gradle завершился без ошибок. Из 1410 проверок 1404 прошли и 6 были пропущены. Две отдельные проверки нативного запуска прошли.
- `bootJar`, `verifyNativeRuntimeCoverage` и `verifyReleaseMetadata` прошли. Проверка состава JAR нашла все четыре целевых набора TDLight natives.
- Независимый Python MCP SDK проверил STDIO, Streamable HTTP, мост HTTP → STDIO и перезапуск локального демона в изолированной среде без Telegram-аккаунта.

### Живая проверка в Berloga

Сборка `1.20.0-9-g50ddb29` прошла проверку поверх существующей авторизованной сессии TDLib. Неверный ожидаемый ID завершает запуск с кодом 3. С верным ID `get_me` вернул ожидаемый аккаунт, а `session doctor` показал `MATCH`.

Одно явно разрешённое сообщение доставлено в тестовый личный чат. Повтор с тем же ключом вернул ту же квитанцию, а журнал записал окончательный ID отправленного сообщения. Ожидание исключило исходящее сообщение. После перезапуска предыдущий курсор вернул `reset=true` и `gap=true`. Отдельный запуск тестовой сборки обработал по сохранённому курсору одно живое входящее сообщение со статусом `settled` и признаком `addressed` для личного чата. Живой QR-вход и групповые упоминания остаются сценариями приёмки.

При проверке отката обнаружилось, что локальный тег Docker `latest` указывал на образ 1.17.0. Старый TDLib после открытия тома новой сборкой завершался с `Wrong version 61`. Сервис восстановлен на официальном образе `1.20.0`, закреплённом по digest. Здоровье контейнера, аккаунт и входящее сообщение после восстановления подтверждены через MCP. Для испытаний с разными версиями TDLib следует использовать только согласованную холодную копию тома. Пока она используется, исходный клиент должен оставаться остановленным. [Выпуск 1.20.0](https://github.com/tolboy/telegram-mcp-tdlib/releases/tag/v1.20.0)

После этого аудита общая диспетчеризация MCP закрыла доступ к журналам, экспортам и квитанциям до проверки аккаунта. Подписки ресурсов используют тот же статус готовности. Для аккаунтов с включённой проверкой теперь действует постоянная привязка метки к подтверждённому ID и сети Telegram. Для старых данных оператор явно указывает владельца. Миграция сохраняет прежние имена файлов, курсоры, ID экспортов и ключи идемпотентности. [Обслуживание сессий](SESSION_MAINTENANCE.md)

В отдельной ветке `codex/mcpb-windows-mvp` собран Windows x64 preview с JVM. Упаковщик проверил манифест, а запуск распакованного файла подтвердил профиль чтения, скрытие отправки и скачивания и штатное завершение процесса. Приёмка установки и обновления в Claude Desktop отложена. Прежняя проверка Desktop проходила через локальный STDIO-мост. [Приёмка от 15 октября](harness-tests/RESULTS_2026-10-15.md)

## TDLib, эксплуатация и серверный стек

- **Обновления TDLight.** Последний релиз Java опубликован как `v3.5.9+td.1.8.68`. Upstream TDLib уже указывает 1.8.70. Автоматическая проверка должна отслеживать публикацию Java BOM, API и natives для всех поддерживаемых платформ. Виджеты стоит начинать после подтверждения нужных типов в собранном артефакте и проверки маппинга на реальных примерах. Для неизвестных типов нужен явный маркер. [TDLight Java](https://github.com/tdlight-team/tdlight-java/releases/tag/v3.5.9%2Btd.1.8.68) · [Upstream TDLib](https://github.com/tdlib/td/blob/master/CMakeLists.txt)
- **Проверяемые преимущества.** Использовать в отчёте о релизе время до `initialize` и до первого полезного ответа, p95 задержки и отмены под нагрузкой, память процесса вместе с JNI, корректность курсоров при перезапуске и долю успешных установок в целевых хостах. Для сравнения JVM и Telethon держать одинаковыми аккаунты, чат, данные, вызовы, условия сети и число клиентов. Публичные числа инструментов и звёзд показывают объём и интерес к проекту.
- **Spring Boot.** Сохранить текущий стек и измерить отдельно обработку HTTP/MCP, JNI и ожидание Telegram через JFR и нагрузочные сценарии. Оценка Ktor или Quarkus имеет смысл, когда профиль показывает вклад Spring в нарушение целевого SLO и прототип воспроизводит безопасность и поведение обеих транспортных веток.
