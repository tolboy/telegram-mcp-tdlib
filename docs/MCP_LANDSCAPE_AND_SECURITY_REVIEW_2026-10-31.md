# Обзор ландшафта MCP и разбор надёжности

Дата: 2026-10-31. Версия проекта по `server.json`: 1.18.0.
Актуализация: 2026-11-01, ветка `hardening/mcp-landscape-followups`. Разделы ниже описывают
исходное состояние до реализации плана, а не отсутствие защит в текущем HEAD.
Текущий статус и результаты повторной проверки: [план](IMPROVEMENT_PLAN_2026-10-31.md)
и [ревью реализации](HARDENING_REVIEW_2026-11-01.md).

При повторной проверке первоисточников 2026-11-01 `latest` действительно перенаправляет
на `2026-07-28`. Утверждения о новой модели HTTP, прежнем session lifecycle,
GitHub toolsets/read-only/exclude и Context7 OAuth остаются актуальными. Числа звёзд
ниже оставлены только как исторические ориентиры: они не пересчитывались и не
обосновывают приоритеты безопасности. Статистика тестов октября также историческая.

### Корректировки выводов при ревью реализации

- Требование явного opt-in при `MCP_READ_ONLY=false` и `approval=off` намеренно шире
  исходной рекомендации про доступные destructive tools. Оно меняет конфигурационный
  контракт старых write-деплоев; утверждать полную обратную совместимость нельзя.
  `auto` запрашивает человека только для destructive-набора, а не для каждой мутации.
- Mutation allow-list ограничивает chat-scoped действия. Он не превращает операции
  профиля, контактов и создания чатов в действия с известным `chat_id`; для них нужны
  ограничения каталога и action grants. Пустой список наследует область чтения.
- Привязка сессии нужна с момента выдачи ID сервером при `initialize`, а не с первого
  произвольного запроса с таким ID. Удаление чужим principal не должно снимать её.
- Каталог инструментов следует фильтровать штатным list-filter SDK до сериализации,
  с учётом доступных аккаунтов. Переписывание HTTP-ответа после servlet chain
  некорректно для асинхронного SSE. Аутентификацию нужно явно переносить из транспорта
  в SDK worker: servlet ThreadLocal сам по себе этого не обеспечивает.
- Отсутствие удобного типа `notifications/cancelled` в SDK — ограничение текущей
  интеграции, а не доказательство невозможности реализации. Передача отмены до TDLib
  остаётся отдельной задачей с проверкой освобождения ресурсов и исхода мутации.
- Текст успешного tool result уже является JSON и совпадает с `structuredContent.data`.
  Произвольный текстовый префикс `untrusted Telegram data` нарушает этот контракт;
  сохраняются структурная метка и аннотации. Защиту от prompt injection они не гарантируют.
- Пустой `server.address` в Spring означает bind на все интерфейсы. Предупреждение
  API-key deployment должно охватывать и этот вариант; OAuth также требует TLS.
- Проверка Windows ACL должна учитывать ALLOW ACE и локализованные SID общих групп.
  Она не равна полной проверке effective access или защите всего дерева TDLib/бэкапов.

Метод: чтение исходников и документации этого репозитория, исходников зависимостей Spring AI 2.0.1 / MCP Java SDK 2.1.0 из локального Gradle-кэша, публичных README и спецификации MCP. Звёзды сверены по страницам GitHub 2026-10-31; это округлённые значения без архивного снимка. Это статический обзор. Динамический пентест, новый прогон тестов, живой прогон Telegram и проверка ответа `/actuator/info` на работающем процессе не выполнялись. Рекомендации ниже не означают, что соответствующие изменения уже реализованы.

Документ дополняет [сравнение архитектур](COMPARISON.md) и [бенчмарк Telegram-серверов от 2026-06-28](PUBLIC_BENCHMARK_AND_ROADMAP.md). Тот бенчмарк смотрит на Telethon/GramJS-конкурентов. Здесь ориентир другой: самые заметные open-source MCP-серверы общего назначения и то, какие их инженерные приёмы ещё не перенесены сюда.

Для инженерного сравнения важнее другое: что модель видит, что она может изменить и что происходит, когда ответ потерялся.

Нужно различать версии протокола. Документация и handshake smoke этого сервера фиксируют `2025-06-18` (`docs/MCP_CLIENT_COMPATIBILITY.md`, `scripts/mcp-streamable-http-smoke.*`). Используемый `WebMvcStreamableServerTransportProvider` из Spring AI 2.0.1 объявляет поддержку версий до `2025-11-25`; это проверка исходников зависимости, не живой handshake. Для текущей модели сессий применима [фиксированная ревизия Streamable HTTP 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Ссылка `latest` на дату проверки уже ведёт на `2026-07-28`. В [этой ревизии HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) убраны протокольные сессии и GET-поток; закрытие SSE означает отмену, а взаимодействия с клиентом идут через MRTR. Переход требует отдельной миграции и проверки хостов. Нельзя добавлять отдельные требования новой ревизии к старому handshake и объявлять совместимость. Зависимости в `build.gradle.kts`: MCP Java SDK 2.1.0, Spring AI MCP 2.0.1, Spring Boot 4.1.1.

## Сильные стороны проекта

Эти решения стоит сохранять. Сравнение с серверами других доменов не устанавливает общее превосходство: модель угроз и чувствительные активы у них различаются.

- Старт в `reader` и `MCP_READ_ONLY=true`. Запись и квотные инструменты убираются из `tools/list`, а не только отклоняются в момент вызова. Повторно проверяются в `McpConfig`, если клиент принёс старый список.
- Разрушительные действия умеют спрашивать человека вне хода модели: elicitation хоста или одноразовая страница на `127.0.0.1`. Генератор Docker с `--writes` фиксирует `elicitation`, чтобы страница не оказалась внутри сети контейнера.
- Изоляция аккаунтов без веерного чтения. Ключ и OAuth-claim ограничивают, какой аккаунт можно выбрать.
- Идемпотентность отправки и исход `UNKNOWN` вместо тихого повтора.
- Бюджет ожиданий TDLib — 50 с при ориентире на клиентский таймаут около 60 с; ожидание человеческого approval исключено из бюджета. Это не жёсткий таймаут всего handler. Flood-gate, bulkhead на 25 одновременных операций и circuit breaker изолированы по аккаунтам; один flood-wait не должен открывать breaker.
- Секреты через `*_FILE`, отказ от symlink и от групповой записи на POSIX, постоянное сравнение ключа, CSRF не отключается только из-за loopback.
- Неаутентифицированный `/auth/**` и `/setup` принимают только прямой loopback и отвергают заголовки пересылки.
- Аудит без аргументов по умолчанию. Нормализация bidi и невидимых символов в тексте Telegram. Поля помечены как недоверенные.
- Поставка: runtime-бандлы, SBOM, подписи образов, checksum native TDLight в `gradle/verification-metadata.xml`.
- Осознанные отказы: сырой MTProto, передача владения, массовый экспорт контактов.

В README полезно явно сказать: сервер применяет политики оператора, но не изолирует модель от инструкций в чужих сообщениях. Playwright прямо предупреждает, что не является security boundary; GitHub называет lockdown фильтром, а не границей авторизации. Здешние ограничения решают другую задачу, и по статическому обзору нельзя объявить защиту в целом сильнее. Содержимое чужих сообщений всё равно доходит до модели как текст.

## Что перенять у лидеров

### 1. Поверхность инструмента важнее числа инструментов

Context7 отдаёт модели два инструмента. GitHub MCP поддерживает toolsets, include/exclude и read-only; read-only и exclude имеют приоритет. По [его документации](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md#scope-filtering), scope-фильтрация при старте работает для classic PAT; remote OAuth запрашивает недостающие scopes, для других токенов каталог не фильтруется. При ошибке определения scopes classic PAT сервер также может показать все инструменты. Playwright предлагает opt-in capabilities и сохранение отдельных результатов в файл (`filename`); фиксированное число инструментов и обязательные диффы снимков здесь не подтверждены.

README указывает полный каталог из 116 инструментов; фактический `tools/list` зависит от конфигурации. Профили `reader`, `inbox`, `community-admin`, `research` решают задачу сужения поверхности, как toolsets GitHub. Возможные улучшения:

- Права из `MCP_PERMISSIONS_FILE` проверяются в момент вызова (`AccessPermissionService.withPermission` внутри `McpConfig`). Каталог регистрируется глобально. При выключенном глобальном read-only клиент с правом только читать видит `ban_user`, если профиль и allow/deny его допускают. Фильтрация по грантам снизила бы шум и число ошибочных вызовов, но не заменяет runtime-проверку. Видимость имени инструмента сама по себе не даёт права выполнить его.
- GitHub lockdown фильтрует контент публичных репозиториев по доверию к автору, с исключениями для доверенных ботов; private repositories не затрагивает. Прямого аналога здесь нет. `TELEGRAM_ALLOWED_CHAT_IDS` решает другую задачу — ограничивает чаты; пустое значение означает «все чаты, доступные аккаунту» (`GuardrailService.isChatAllowed`). Чужие группы — канал prompt injection. Предлагаемое усиление — отдельный режим записи только в явно указанные чаты. Это граница действий, а не фильтрация авторов по примеру lockdown.
- Длинные ответы уже имеют бюджет, пагинацию и сохраняемые export jobs. У Playwright полезен приём ответа в файл; выдача такого файла удалённому клиенту потребует отдельного авторизованного канала, локальный путь не гарантирует доступность. Прогресс MCP — самостоятельная рекомендация, его наличие у Playwright по рассмотренным источникам не установлено. Progress улучшает UX, но не гарантирует продление таймаута хостом.
- Составные фасады (`message`, `chat`, …) в бенчмарке от 2026-07-26 отложены до замеров. Аннотации MCP относятся ко всему tool, а не к отдельному значению аргумента `action`. Поэтому фасад, смешивающий чтение и бан, не может честно объявить `readOnlyHint=true` для всех вызовов. Сам фасад не обязан ломать подтверждение: оно сохранится, если применять политику к внутреннему действию. Рекомендация — не переносить проверки только на имя внешнего tool.

### 2. Протокол, который хосты уже умеют

В коде приложения не зарегистрированы ресурсы и промпты, не вызываются sampling и уведомления `notifications/progress` / `notifications/message`, нет явной обработки `notifications/cancelled`. Это вывод об интеграции приложения: SDK имеет собственную поддержку протокольных возможностей, и поиск только по `src/main/kotlin` не доказывает их отсутствие в транспортном стеке. Перед выводом об отмене нужен тест прохождения сигнала до handler и TDLib. Часть возможностей отложена сознательно в бенчмарке: sampling и клиентские логи расширяют канал передачи текста Telegram.

Имеет смысл добавить другое:

- **Промпты MCP** для уже написанных рецептов (`summarize-inbox`, `find-lost-message`, `safe-draft-reply`). Хост показывает их как готовые команды. Отдельный skill при этом остаётся. Промпт не даёт модели новых прав.
- **Roots.** Client roots — согласование области работы, не самостоятельная песочница. Здесь `FileSecurityService` использует только операторский `MCP_FILE_ROOTS`. Если добавить roots клиента для сужения в сессии, эффективной областью должно быть пересечение с операторскими roots, без расширения прав и без открытия файловых операций при пустом `MCP_FILE_ROOTS`. В удалённом HTTP локальные пути клиента могут вообще не существовать на сервере.
- **Прогресс и отмена.** `wait_for_changes` ждёт до 30 с, transcription и bounded export могут ждать TDLib. `ExportJobService` уже работает пошагово: `resume` читает максимум одну страницу, `cancel` отменяет job; это не отмена текущего JSON-RPC запроса. Нужен тест отмены во время ожидания TDLib с освобождением занятого слота. Для текущего HTTP разрыв соединения не равен `notifications/cancelled`; в ревизии `2026-07-28` семантика другая.
- **Привязка сессии к аутентификации.** [Security best practices для 2025-11-25](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) рекомендуют связывать session ID с идентичностью пользователя, полученной из проверенного токена. Это не требование claim `cnf`: тот относится к подтверждению владения ключом. HTTP-аутентификация проверяется на каждом запросе, но в приложении нет явной привязки владельца MCP-сессии. Проверять следует попытку клиента B использовать session ID клиента A со своим валидным ключом. При миграции на `2026-07-28`, где протокольные сессии удалены, рекомендацию нужно пересмотреть.
- **Заголовки маршрутизации.** Требования SEP-2243 включены в HTTP ревизии `2026-07-28`: `Mcp-Method` для запросов, `Mcp-Name` для определённых методов, сверка с телом и отказ 400 при нарушениях. Это часть миграции протокола; отсутствие таких заголовков у клиентов `2025-06-18` / `2025-11-25` само по себе не нарушение этих старых ревизий.
- **Прогон [modelcontextprotocol/conformance](https://github.com/modelcontextprotocol/conformance)** на поддерживаемой ревизии в CI. Handshake-скрипты действительно ограничены `initialize` / `tools/list`, но `scripts/mcp-result-smoke.py` уже подключён в `.github/workflows/ci.yml` и `docker-build.yml`: вызывает `_manifest` и `get_me` без Telegram credentials, проверяет успешный результат, ожидаемую ошибку, output schema и annotations. Это закрывает прежний пробел проверки tool result, но не заменяет conformance и живой Telegram canary.

Ресурсы MCP для списка чатов и ленты сообщений лучше не включать в поверхность по умолчанию. Чтением ресурсов управляет приложение-хост; нельзя предполагать отдельное согласие пользователя на каждый fetch. Для пользовательского аккаунта это дополнительный канал выдачи переписки. Если ресурсы появятся, предлагаемый безопасный старт — opt-in, метаданные без текста и те же проверки доступа, что у tools. Это проектная рекомендация, не запрет спецификации.

### 3. Локальный вход без секрета в конфиге клиента

Локальный GitHub MCP умеет OAuth в браузере и держит токен в памяти, не в `mcp.json`. Здесь QR-мастер убирает ручной ввод кода в shell, но TDLib-сессия сохраняется на диске: это не аналог токена только в памяти. Генератор `ClientConfigPrinter` использует `TDLIB_API_HASH_FILE` для локального процесса, а в Docker-аргументах заменяет его на `TDLIB_API_HASH=<your-api-hash>`. Именно Docker-путь требует доработки: монтировать отдельный файл секрета и ссылаться на него внутри контейнера. Существующие файлы секретов также требуют защиты правами ОС.

У Context7 [hosted `/mcp` принимает API key, а `/mcp/oauth` поддерживает OAuth](https://context7.com/docs/resources/all-clients#oauth-authentication); stdio использует API key. Здесь `MCP_AUTH_MODE` выбирает HTTP-аутентификацию, а stdio полагается на изоляцию процесса, поэтому это не такое же разделение. Генератор Claude Desktop remote отвергает `--client claude --http` без OAuth; совместимость прямого remote OAuth остаётся непроверенной в локальной матрице.

## Безопасность

Ниже находки статического разбора. Эксплуатируемый удалённый сценарий при настройках по умолчанию (loopback, read-only, `reader`, без ключа только с той же машины) не продемонстрирован. Это не доказательство отсутствия риска: read-only разрешает чтение переписки, а вредоносный контент может влиять на модель и при локальном запуске. Запись и публикация порта увеличивают последствия; доступ к файлам сессии — отдельный локальный риск. Уровни ниже — операционные приоритеты, не CVSS подтверждённых уязвимостей.

### Высокий операционный риск

**Подтверждение разрушительных действий по умолчанию выключено.** `MCP_READ_ONLY=true`, а `MCP_DESTRUCTIVE_APPROVAL=off` (`application.yml`). При выключении read-only и выборе профиля, открывающего destructive tools, остаётся только `MCP_CONFIRMATION_REQUIRED=true`: аргумент `"confirmed": true` может поставить сама модель. Это прямо написано в `docs/TOOL_PROFILES.md`. Генератор `--writes` включает `auto` для локального процесса и `elicitation` для Docker. Сам сервер сочетание «destructive tool доступен, человек не спрашивается» не запрещает. При этом approval защищает только набор destructive tools из `OperationGuardService`, а не каждую запись: например, обычный `send_message` в него не входит.

Рекомендация: при доступных destructive tools и `approval=off` требовать явного opt-in либо режим `auto` / `elicitation` / `loopback`. Возможное имя нового флага — `MCP_ALLOW_MODEL_CONFIRMED_WRITES`; сейчас его нет. Это намеренное изменение поведения и конфигурационная миграция для существующих write-деплоев, а не автоматическое сохранение обратной совместимости. Если требуется согласование всех мутаций, набор защищённых действий нужно расширять отдельно.

**База TDLib на диске без настраиваемого приложением ключа шифрования.** В `TdLibProperties.Database` задокументировано ограничение используемого `SimpleTelegramClient`; отдельный ключ приложение не передаёт. `td.binlog` — файл в каталоге сессии, не каталог. Копию действующей сессии следует считать потенциальным захватом аккаунта до отзыва авторизации. Защита включает права доступа ОС, шифрование тома/каталога и отдельную защиту бэкапов; шифрование тома не защищает от процесса с правами пользователя на разблокированной машине. Браузерные MCP также могут сохранять cookies и профили, поэтому хранение таких активов не уникально для Telegram.

Рекомендация: исследовать передачу ключа TDLib через API выбранной версии библиотеки и файл/OS secret store; возможность и объём переделки не проверены. До этого — предупреждение, каталог с правами только владельца, защищённые бэкапы и исключение каталога сессии из `MCP_FILE_ROOTS`, чтобы доступный upload не мог прочитать его файлы. Само чтение ключа из файла не защищает от компрометации пользователя процесса.

### Средний риск

**Проверка `Origin` не подключена в используемом транспорте.** Спецификация Streamable HTTP требует 403 при присутствующем недопустимом `Origin`. Проверены не только `SecurityConfig` / YAML, но и исходники Spring AI 2.0.1: `WebMvcStreamableServerTransportProvider.Builder` по умолчанию использует `ServerTransportSecurityValidator.NOOP`, а `McpServerStreamableHttpWebMvcAutoConfiguration` не переопределяет его. MCP Java SDK 2.1.0 уже содержит `DefaultServerTransportSecurityValidator` для Origin/Host; наличие класса не означает включённую защиту.

CSRF для keyless loopback не отключён, а для проверенных header credentials есть исключение. Обычный cross-origin JSON POST обычно требует CORS preflight, но DNS rebinding может сделать запрос same-origin с точки зрения браузера. Поэтому нельзя считать отсутствие CORS достаточным доводом против rebinding. Неправильный Origin после rebinding тоже не гарантирован; полезна проверка допустимого Host. Эксплуатация полного стека с CSRF здесь не проверялась.

Рекомендация: подключить валидатор Origin/Host на `/mcp`, явно задать политику разрешённых значений и тесты 403 для GET/POST/DELETE с недопустимым Origin. Проверить запрос с валидным ключом, чтобы CSRF не маскировал отсутствие Origin-проверки. Отсутствие Origin не должно само по себе ломать небраузерных клиентов. Не включать CORS с произвольным отражением origin.

**Права клиента не сужают объявленный каталог.** См. раздел про toolsets. Это улучшение минимизации поверхности и UX для общего демона, а не подтверждённый обход авторизации. Ограничения проверяются при исполнении; скрытие инструмента должно дополнять эту проверку.

**Пустой allow-list чатов равен полному аккаунту.** Удобно для первого запуска в read-only. Для профиля с записью это широкая поверхность. Режим «мутации только по allow-list, чтение шире» совпадает с тем, как GitHub отделяет lockdown (фильтр содержимого) от scope токена (граница действия).

**Секреты на Windows не проверяют ACL.** `SecretResolver.validatePosixPermissions` при отсутствии POSIX-атрибутов выходит без проверки. Смонтированный секрет с доступом Everyone на Windows будет прочитан. На POSIX групповое чтение только предупреждение, запись группой запрещена. Для каталога TDLib отдельной проверки владельца нет.

**Файл переопределений anti-spam.** Относительный `anti-spam-overrides.json` уже разрешается внутри `PlatformPaths.applicationDataDirectory`, не cwd (`AntiSpamPolicyService.overridesPath`). Подложить файл можно при праве записи именно в каталог данных или явно настроенный путь. Отдельной проверки прав/симлинков этого файла нет. Потолки заданы не для всех инструментов и не для всех полей правила. `setOverride` из MCP не вызывается, загрузка — при старте. При повреждённом JSON логируется предупреждение и остаются базовые/YAML-правила, с применением настроенных ceilings; ранее заданные более строгие overrides могут пропасть. Это не безусловный обход лимитов и не безусловно безопасный отказ. Рекомендация: проверка прав, общие ceilings/floors для всех полей и отказ старта при повреждении явно заданного policy-файла.

**Bulkhead и rate limiter общие для клиентов одного аккаунта.** `TdLibClientService` создаёт bulkhead на аккаунт: 25 одновременных операций по умолчанию (`tdlib.requests.max-concurrent-calls`). `TdLibConfig` создаёт отдельный rate limiter с конфигурацией 30 разрешений/с и отдельный breaker для каждого аккаунта. Следовательно, это не единые лимиты на процесс. Клиенты одного аккаунта всё ещё конкурируют между собой; нужен дополнительный лимит на principal с сохранением общего аккаунтного потолка. Лимит разрешений/с не равен гарантированному числу завершённых вызовов/с.

**`/actuator/info` разрешён без аутентификации в security chain.** `permitAll` перечисляет health, info и два конкретных well-known endpoint, а не весь `/.well-known/*`. `management.info.env.enabled=true`, `git.mode=full`. Env-contributor относится к свойствам `info.*`, не ко всему environment. Полнота git-данных зависит от наличия `git.properties`; настройка `full` сама их не создаёт. `/actuator/env` не exposed, prometheus/metrics требуют аутентификацию. Живой JSON info здесь не снимался. Рекомендация: проверить фактическое содержимое info и при необходимости ограничить его или требовать ключ.

**Аудитория контента `user`.** `ToolSupport` помечает текст аудиторией USER и сознательно не ставит дробный priority: часть сборок Codex отвергала весь ответ. Аудит от 2026-10-15 уже считает это риском интерпретации хостом. На одном хосте модель может не увидеть текст сообщения. На другом пометка игнорируется, и инструкция из чата доходит целиком. Нормализатор не вырезает фразы-инструкции и не должен: это ложная защита. Надёжный контур — узкий каталог, allow-list и подтверждение человеком. Пометку стоит дублировать конвертом в самом тексте (`untrusted Telegram data`), который остаётся и в text, и в structuredContent.

### Низкий риск и то, что уже закрыто хорошо

- Мастер входа: CSP разрешает inline scripts/styles; nonce авторизации передаётся в query. Внешних ресурсов нет, QR строится локально; `Cache-Control: no-store` уже установлен для страницы и QR. URL всё равно может попасть в историю браузера или логи. Усиление: явный `Referrer-Policy: no-referrer` и CSP nonce/hash для inline-кода либо отдельные same-origin assets. CSP nonce должен быть отдельным случайным значением, не секретом авторизации; это defense in depth, не устранение доказанной XSS.
- Если оператор передаёт `TDLIB_AUTH_CODE` / `TDLIB_2FA_PASSWORD` через Docker env или сохраняет в клиентском конфиге, они доступны в соответствующей конфигурации. Файловые варианты есть; `ClientConfigPrinter.environmentEntries` эти код и пароль уже не генерирует.
- Образ слушает `0.0.0.0` внутри контейнера (`Dockerfile`); README публикует `127.0.0.1:8080`. Keyless-режим отвергает не-loopback peer и forwarding headers. Публикация с API key делает порт доступным сети, но не снимает проверку ключа: это не автоматический захват аккаунта. Для внешнего HTTP нужны TLS, защита ключа или OAuth, scoped grants и проверка proxy-настроек. OAuth с bearer token также не заменяет TLS.
- Сравнение ключей постоянное по времени. Дубликаты имён инструментов валят старт. Неизвестные имена в allow/deny валят старт. Симлинки секретов отвергаются. Файловые пути: запрет `..`, канонизация через `toRealPath`, пустые roots запрещают операции.
- Зависимости TDLight идут с `mvn.mchv.eu`, с ограничением Maven group и checksum verification. Checksum фиксирует одобренные байты, но не доказывает их безопасность. Смена зеркала технически возможна без смены библиотеки при сохранении и проверке тех же артефактов. SBOM и cosign настроены в `.github/workflows/docker-build.yml`; это проверка release-конфигурации, а не подписи конкретного опубликованного образа.

Копировать не стоит:

- `browser_run_code_unsafe` и любые «выполнить произвольный MTProto/JS».
- Исключение «доверенный бот всегда безопасен», как у GitHub для `github-actions[bot]`. Служебные чаты Telegram так не устроены.
- Общую формулировку Playwright «ограничения origin не являются границей». Здесь allow-list чатов и файловые roots как раз должны остаться границей, с тестами на обход.

## Надёжность

В коде и тестовых сценариях есть бюджет ожиданий TDLib, классификация flood и локальных прерываний, защита от одновременного использования сессии с кодом выхода 2, идемпотентные отправки и журнал исхода. Конфигурация задаёт graceful shutdown 30 с на фазу Spring; это не доказательство общего времени завершения процесса. Docker healthcheck в stdio делает успешный no-op, а не проверяет живую сессию Telegram. Тесты в рамках этого обзора не запускались.

Пробелы, которые видны на фоне серверов без локальной сессии (GitHub remote, Context7):

| Тема | Сейчас | Что даёт сбой |
|---|---|---|
| Один процесс TDLib на базу | Замок сессии, для нескольких клиентов нужен daemon | Второй stdio-процесс клиента падает. Это задокументировано. Лидеры с удалённым HTTP этого класса проблем не имеют |
| Отмена клиентом | Нет явной интеграции отмены MCP с TDLib в приложении; job cancel существует отдельно | Освобождение ресурсов по Stop не проверено. Уже отправленную мутацию отмена не откатывает; повтор без того же idempotency key может создать дубль |
| Долгие инструменты | Бюджет ожиданий TDLib 50 с; approval исключён; export jobs выполняются по одной странице за resume | Нет общей гарантии ответа handler за 50 с. Approval по loopback может ждать ещё до 120 с по умолчанию. Нужна проверка реальных таймаутов хоста; `PENDING` не является универсальным результатом любого долгого вызова |
| Тесты | Большой набор на моках. Полный прогон из аудита 2026-10-15: 802 passed, 2 skipped | Это не проверка живого Telegram. Повтор живого сценария не встроен в релизный контур |
| Совместимость хостов | Codex, Hermes, Claude Desktop через мост — точечные прогоны 2026-10-15. Cursor упёрся в лимит модели | Матрица в `MCP_CLIENT_COMPATIBILITY.md` помечает непроверенное. Популярность других проектов не доказывает отсутствие регрессий; здесь нужен свой canary |
| macOS Intel | Сборки нет, пока нет классификатора TDLight | Дыра дистрибуции, не протокола |
| Повреждение overrides JSON | Старт продолжается с предупреждением, действуют base/YAML и настроенные ceilings | Более строгие правила из overrides могут не примениться; ceilings из YAML не исчезают |

Предлагаемый canary: отдельный тестовый аккаунт, раз в релиз, stdio с реальным `get_me` и одной страницей истории, плюс HTTP с тем же. Привязать проверку к ожидаемому user/chat ID; credentials и сохранённую TDLib-сессию держать в защищённом secret store/изолированном runner, переписку не публиковать в CI artifacts. При наличии стабильного защищённого runner падение canary может блокировать релиз. `scripts/mcp-agent-features-smoke.py` уже содержит живые сценарии, но не подключён как обязательный release gate. Ошибка разбора ответа Codex при зелёных JVM-тестах из аудита 2026-10-15 показывает, почему нужен также независимый SDK/host smoke; offline result smoke теперь есть.
